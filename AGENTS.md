# AGENTS.md

## Repository Shape

- WLS is a multi-project monorepo, not one root build: there is no root `pom.xml` or root `package.json`; run tools in the changed project directory.
- `wls-common/` is the only multi-module Maven reactor (`exception`, `monitoring`, `security`, `testing`, `swagger`). Services depend on released `de.muenchen.oss.wahllokalsystem.wls-common:*` versions, so in-repo `wls-common` changes do not affect services until a release/version bump.
- `wls-gui-wahllokalsystem/` and `wls-gui-admintool/` are separate Vue/Vite apps with their own `package-lock.json`; run npm commands in the affected app, not at repo root.
- `docs/` is a separate VitePress project. Architecture and conventions live under `docs/src/technik/`; check these before guessing patterns.
- `stack/` contains local Docker/Podman compose, gateway/auth/db config, and seed HTTP requests.
- `wilma/server_mock/` is a separate Express mock backend for frontend development; it has its own `package.json` and mutable JSON data under `data/`.

## Verification Commands

- Backend/service or gateway full CI check: `mvn -B -ntp -f <project>/pom.xml verify` from repo root, or `mvn clean verify` inside the project.
- Backend focused tests inside a service: `mvn test`, `mvn test -Dtest=ClassName`, or `mvn test -Dtest=ClassName#should_returnDTO_when_givenValidId`.
- Backend formatting/linting inside a service: `mvn spotless:apply` before verify when editing Java; `mvn checkstyle:check` for Checkstyle only.
- `wls-api-gateway` has stricter Maven verification than most services: compiler `failOnWarning`, Spotless, PMD/CPD, SpotBugs, and FindSecBugs run in `verify`.
- Frontend CI order inside the changed GUI: `npm ci` if dependencies are not installed, then `npm run lint`, `npm run test`, `npm run build`.
- Frontend dev: `npm run dev`; main GUI serves on `8400`, admintool on `8401`, both proxy `/api` and `/actuator` to `localhost:8083`.
- Docs checks inside `docs/`: `npm run lint`, `npm run build`.

## Toolchain Gotchas

- Backend is Java 21 / Spring Boot 3.5.x; GitHub Actions use Temurin 21.
- Frontends require Node `>=24.11 <25`; CI uses Node `24.11.1`.
- Spotless runs in Maven `verify` and uses `itm-java-codeformat`; most services also apply googleJavaFormat. Unformatted Java fails the build.
- MapStruct is configured with `defaultComponentModel=spring` and `unmappedTargetPolicy=ERROR`; adding target fields without mapper updates fails compilation.
- Lombok, MapStruct processor, and `lombok-mapstruct-binding` are on the annotation processor path; do not remove or reorder casually.

## Generated Code

- Frontend API clients are generated from `src/resources/openapis/*.json` via `npm run gen:<service>-api` into `src/api/wls-clients/generated-*-api/`; do not edit generated client files by hand.
- Backend Java clients are generated by `openapi-generator-maven-plugin` from `src/main/resources/openapis/*.json` during Maven builds; generated packages follow `<service>.clients.<target>.(api|model)` or older service-specific packages, so keep handwritten adapters/mappers outside generated packages.
- OpenAPI generator gotcha: controller path variables must be explicit method parameters, not bundled into one parameter object, or generated OpenAPI can omit path parameter metadata.

## Backend Patterns

- Base package is `de.muenchen.oss.wahllokalsystem.<service>service`; entrypoint is usually `MicroServiceApplication`.
- Services are organized by domain across three layers: `rest/<domain>` for controllers, DTO records, and DTO mappers; `service/<domain>` for business services, validators, models, model mappers, and client interfaces; `domain/<domain>` for JPA entities and repositories.
- A service may use either separate controller/service models or shared controller/service models, but do not mix both styles inside one service.
- Cross-domain types belong in a `common` subpackage of the relevant layer.
- External service calls are hidden behind service-layer `*Client` interfaces and implemented under `client/` or `clients/`; standalone runs use `DummyClientImpl` with the `dummy.clients`/`standalone` profile.
- Authorization is normally both `hasAuthority(...)` and a Wahlbezirk permission check through `BezirkIDPermissionEvaluator`; local/test profiles may use `DummyBezirkIdPermissionEvaluatorImpl`.
- Use WLS exception types for HTTP errors: `FachlicheWlsException` maps to 400, `SicherheitsWlsException` to 403, infrastructure/technical exceptions to 500 via `GlobalExceptionHandler`.
- Flyway scripts are under `src/main/resources/db/migrations/{h2,oracle}`; SQL keywords uppercase, table names UpperCamelCase, columns lowerCamelCase.

## Backend Tests

- Test names use `should_<expectedResult>_when_<stateUnderTest>` in English and CamelCase.
- Group backend tests with JUnit `@Nested`, especially by method under test; ArchUnit enforces naming/package rules from `wls-common:testing`.
- When endpoints or permissions change, update `configuration.SecurityConfigurationTest`, the relevant `service.<Domain>SecurityTest`, and controller integration tests, not just unit tests.
- Do not change `ArchUnitTest` for ordinary feature work unless the architecture rule itself changes.

## Frontend Patterns

- Vue 3 Composition API only; `wls-gui-wahllokalsystem` disables the Options API in Vite, while `wls-gui-admintool` enables it only in development for devtools.
- Source is domain-partitioned across `api/`, `components/`, `composables/`, `stores/`, `views/`, `types/`, `plugins/`, `service-worker/`, and `resources/openapis/`; `tests/` and `stories/` mirror `src/` paths.
- Component hierarchy matters: Views and `The...` single-use components may use stores; `Base...` components must stay props/events only and should use composables only for formatting/validation.
- Backend access should flow `store -> service composable -> client + mapper`, matching the documented frontend architecture.
- Use `data-test` attributes for test selectors; values are selectors, not IDs.
- Component tests verify rendering snapshots and event handling; tests use `it(...)`, not `test(...)`.
- Prefer `defineModel()` for Vue two-way binding; Storybook stories must manually document `modelValue` and `onUpdate:modelValue` in `argTypes` because Storybook does not infer them correctly.
- Main GUI PWA uses a custom service worker at `src/service-worker/wahl-worker.ts`; offline behavior is a core feature.
- User-facing UI text and most domain terms are German; keep established German domain terminology rather than translating it.

## Local Run Notes

- Service scripts run Maven with local profiles: `./runLocal.sh` uses `local,standalone`; `./runLocalNoSecurity.sh` adds `no-security`.
- Fixed local service ports are documented in `docs/src/technik/get_started/index.md`; only one instance of each service can run because IDE and Podman use the same ports.
- Full local stack startup order from docs: Oracle DB, auth-service, api-gateway, frontend, then domain services; seed with `stack/http_requests/initOracleDB_Komw.http` or `initOracleDB_MBW.http`.
- Required hosts entries for local stack: `127.0.0.1 host.docker.internal`, `127.0.0.1 auth.wls.host.docker.internal`, `127.0.0.1 gui.wls.host.docker.internal`.
- For frontend development, use `http://host.docker.internal:8083`/`http://localhost:8083` login flow and access the Vite app on `localhost:8400`; HMR does not work through `gui.wls.host.docker.internal:58083`.

## Process Notes

- PR workflows are path-scoped per service/app and call the same local checks above: Maven `verify` for backend projects and `lint -> test -> build` for frontends.
- Default branch/PR target is `dev`; commit/PR text convention references an issue like `#791 - ...`.
- PR checklist expects docs updates when behavior/public API changes, Swagger/OpenAPI updates for backend API changes, and maintained example HTTP requests where relevant.
